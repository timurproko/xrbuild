# XR Build UI design system

`design-system.css` is the visual source of truth for XR Build developer tools. `style.css` contains only control-panel product layout and feature-specific presentation.

## Appearance and case gallery

The Settings menu always opens **All** when plugin settings are available, independent of the last sidebar choice. Explicit `?module=` links still open their module (including after reload/canonical redirects); when there are no plugin settings the core section is the only destination.

Core settings (Apps, marked core) exposes **Theme: System / Light / Dark**. System is the default; explicit choices apply immediately and persist in browser-local `panel.theme`, not workspace/runtime configuration. Load `/theme.js` before styles to apply the saved choice before paint. The bootstrap also synchronizes same-origin tabs/frames. CSS-only consumers retain automatic system appearance.

The **Dev shortcut** (or equivalent repository-development CLI) adds **Design** to the app menu; normal user/auto launches do not. Visibility follows the running process's launch mode, not a browser query or workspace preference; an existing process is never restarted or taken over to switch it. The gallery URL is `/design`; `/design-system.html` redirects there with its query preserved (menu visibility is not an authentication boundary).

**Design** follows **Settings** directly, without a divider between them; the existing separator precedes Restart/Rebuild. The gallery uses the same full **XR Build · Design** app bar/product menu as other pages, including explicit Restart/Rebuild via shared handlers. A separate-origin preview follows those maintenance links back to the selected panel rather than issuing cross-origin mutations. There is no subtitle or visible Cases label. Registered tools load the same read-only panel navigation metadata, and the gallery shell reads it once so app/tool links stay available across routes. Its accessible case dropdown defaults to **Main**, the shared component catalog. Categories cover typography, buttons/actions, fields/controls, navigation, status/feedback, dialogs/progress, layout/content and media/output. All are shown on one page; category selection scrolls to the relevant section. No redundant Main heading or subtitle appears inside the page. **Install dependencies** remains a separate checklist/progress case with compact scenario rows. Register new cases in `design-system/gallery.js`; the selector is generated from that registry. Resize/reload the browser normally—there are no separate View/Theme/Width/Reload controls. Dependency preview frames contain only the background and dimmed real dialogs. Main examples use the actual shared CSS/modules; dropdowns, tabs, steppers, switches, tooltips, menus and dialogs are interactive locally, and sample progress completes without a process. Main is mounted in the serving document with the same workspace/sidebar/card-stack templates and document scrollbar as Apps; it is not a separately padded iframe. Its examples use scoped local handlers and independent shared dialog instances, so mock job IDs/callbacks never mix with shell maintenance. Workflow install/build requests remain simulated in memory, with isolated case-frame CSP blocking real API connections/forms. Only the gallery shell reads navigation metadata or performs maintenance after an explicit menu click. The component catalog demonstrates the documented shared primitives, not device/provider/client workflows; project-specific workflows have their own cases. Case styles own only gallery layout, never copied theme palettes or controls.

A separate-origin standalone preview has its own browser preference; use the same-origin gallery when checking a choice made in core settings.

## Scrolling

The shared module installs one per-document overlay-scrollbar controller. Page, list, log, dropdown and dialog tracks share `--xrb-scrollbar-*` geometry and colors, draw over content, and reserve no gutter. Native overflow remains the scroll engine (wheel/touch/focus scrolling); tracks support pointer dragging and Arrow/Page/Home/End keys with scrollbar ARIA semantics. Tracks have no focus outline; keyboard focus accents the thumb instead. Multi-select lists remain open while their track is dragged. Changes to content/visibility/layout update the tracks, removed regions are released, and modal tracks stay above their own dialog. No product should copy native scrollbar skins or rely on deprecated `overflow: overlay`.

`installOverlayScrollbars(document)` is idempotent and returns a disposer that restores native gutters. CSS-only consumers, unsupported documents and forced-colors mode keep native scrolling. Use `data-xrb-scrollbar="none"` only for an intentional trackless region. Bootstrap/static adapters serving the shared module must also serve `scrollbars.js` and `workspace-layout.js`.

## Components

- `xrb-app-bar` + `xrb-brand` + `xrb-product-menu`: application shell and product navigation. `xrb-app-bar--wrap` is the shared responsive toolbar variant. `installWorkspaceLayout(document)` measures the actual header (including wrapping) once for shared sticky offsets.
- Workspace templates: `xrb-workspace-layout` owns outer top/inline/bottom spacing; `xrb-workspace-grid` owns max width and centering; `xrb-workspace-grid--sidebar` and `xrb-workspace-grid--activity` share sidebar sizing and responsive collapse. `xrb-workspace-flow` stacks activity/content groups at reduced widths. Products choose topology, not copied width/padding/breakpoint rules.
- `xrb-workspace-sidebar` + `xrb-workspace-sidebar-heading` + `xrb-workspace-sidebar-content` own sticky sidebar height, heading rhythm and inner scrolling. `xrb-card-stack` owns the same `--xrb-card-gap` rhythm in Apps and Main, with no extra child-card margin.
- `xrb-section-label`: column/section heading geometry. Typography specimens begin with Dialog heading, then Page heading, with secondary/help text below.
- `xrb-choice-list`: compact borderless choice/navigation rows with muted idle text and a subtle accent-soft selected state; standard keyboard focus/hover behavior remains.
- `xrb-card`: bordered surface. Direct paragraph children use the card's shared gap rather than native paragraph margins. `xrb-inline-icons` groups icon buttons inline without a product-specific margin override.
- `xrb-progress-status` + `xrb-progress-status-icon`: shared dialog icon/title/description header. Desktop setup uses a decorative 28px setup icon and the same normal muted body text as progress descriptions, with the shared 4px heading gap. Do not style main dialog descriptions as small field help. Setup action captions capitalize their first letter and keep one ellipsis without rewriting job metadata.
- `xrb-tabs` + `xrb-tab`: tab navigation.
- `xrb-tab-toolbar`: one heading row with tabs left, `.xrb-tab-toolbar-center` contextual filters centered, and `.xrb-tab-toolbar-end` actions right. Only tabs belong in the ARIA tablist; swap filters/actions alongside their panel without duplicating inner toolbars. The center scrolls horizontally when narrow. Activity X clears log/finished jobs; it never closes Activity or stops active work.
- `xrb-glyph-detail`: detail-preserving, theme-specific tint for opaque emoji artwork; silhouette tint would erase internal detail. Settings Apps and the Apps favicon share one emoji identity and the `--xrb-glyph-detail-filter` theme tint.
- Toolbar trailing icon buttons keep their full 28px hit area; optical compensation aligns the visible clear glyph with the leading tab text's edge inset.
- `xrb-focus-inset`: keyboard focus stays inside clipped navigation surfaces. Sticky masks use `--xrb-sticky-mask-gap`, shorter than the heading/card gap, so selected borders remain visible.
- `xrb-sidebar-content` + `xrb-sidebar-section`: consistent tab-panel top spacing, scrolling, scrollbars, and first-section margin reset for tool sidebars.
- Display choices use the operating system's friendly monitor name or Built-in display only for a confirmed internal connector. Missing/generic names use Primary display / Display N; raw GDI paths remain internal routing metadata, not visible captions. Being the primary screen alone does not establish that it is built in.
- `renderField(labelHtml, controlHtml, {hint, error})` is the shared field wrapper. Trusted label/control markup stays together with escaped description/error slots inside `xrb-field-label`; the standard field-gap token owns description spacing and width. Core Cursor and plugin dropdown/number fields use this path instead of form-level paragraphs or HTML-replacement helpers.
- Ordinary input/select/dropdown values share the same sans-serif family, size, weight and line height. Disabled/read-only values may change color/opacity, not typography; publication version fields have no monospace override. Inline title editing inherits its surrounding title, while code/output stays monospace.
- The app-header Run dock appears only when the current action is above the app bar; below-viewport or animation-clipped actions never trigger it. Re-rendered targets replace stale observations without flashing identity/metrics.
- Buttons size to their content by default, including primary buttons. `small` / `xrb-controls-small` is the single reduced size; the old Compact class is an identical compatibility alias, not a separate design variant. Tool-icon wrappers center SVGs with the text. Range controls omit the outer focus rectangle but retain a thumb-level keyboard focus ring. Warning/error banners share padding, text metrics and rounded corners, differing only in tone. Maintenance menu text stays foreground; only its status bulb carries warning/rebuild color.
- Shared controls: buttons, fields, checkboxes, `xrb-switch`, `xrb-toggle-pill`, `xrb-segmented`, `xrb-filter-chip`, `xrb-swatch`, `xrb-tool-button`, `xrb-range`, dialogs and dialog headers/actions, the borderless `xrb-progress-dialog`, the styleable dropdown/listbox component, shared checkbox/checkmark geometry (including multi-select menus), automatically enhanced `xrb-number-control` steppers, `xrb-icon-button` actions, shared SVG icons, and portal tooltips.
- Field labels align content at the top and field grids top-align each label/control group, so validation help never stretches title-to-control spacing or shifts the neighboring control. Checkbox grids use an 8px row gap and the shared stack gap between columns. Color groups have no leading divider.
- Layout: spacing tokens (`--xrb-space-field`, `--xrb-space-stack`, `--xrb-space-section`) feed `xrb-stack`, `xrb-control-group`, `xrb-button-row`, `xrb-field-grid`, `xrb-toggle-grid`, `xrb-sidebar-content`, and `xrb-sidebar-section`; products should not add margins between component children.
- Reveal motion: `setRevealed()` animates conditional blocks with shared height/fade motion, can resume from an elapsed time after re-rendering, and respects reduced-motion preferences.
- `xrb-help`: secondary helper text. Add `field-error` for validation: inputs and dropdowns keep their normal surface/focus treatment while the helper typography changes to the semantic error color. `enhanceHelpText()` normalizes plain helper copy to a capitalized sentence ending in a period.
- Content: `xrb-supporting-text`, `xrb-code-block`, `xrb-disclosure`, `xrb-section-label`, and `xrb-inline-edit` own repeated supporting copy, readouts, disclosure headings, title dividers, and inline editing.
- Media and data: `xrb-media-stage` + `xrb-media-empty` provide one camera/depth preview frame and no-feed state; `xrb-empty-state` standardizes empty output; `xrb-key-value-list` provides compact label/value columns.
- Header maintenance labels carry `data-maintenance` matching shared menu IDs. `MAINTENANCE_ACTIONS` defines the menu order (Restart, then Rebuild), and `orderMaintenanceLabels()` applies that logical order to existing header nodes without recreating their state/bindings. Default markup follows the same order, including when either label is hidden.
- Shared maintenance: `restartPanelInPlace()` keeps the progress modal and reload on the active tool route instead of navigating to the Control Panel. `rebuildProgressDialog()` supports a contained instance with an `idPrefix`, so local examples reuse the real component without sharing IDs or real job callbacks; dispose contained instances when their owner is removed.
- `design-system.js`: `installDropdowns()` for generated `.dropdown` controls, `enhanceSelects()` for native single-selects, `installNumberSteppers()` to enhance every numeric input with shared step controls, `setFieldError()` to place and clear shared validation for inputs/dropdowns, `installTabs()` for the animated shared tab indicator, `iconSvg()` / `installIcons()` for shared icons, `positionFloating()` / `openFloating()` for bounded menus and their initial focus, `resumeAnimations()` for resumed component motion, `installTooltips()` for unclipped custom tooltips, and `enhanceHelpText()` for shared helper copy.
- Tooltip hints: use `data-tooltip` for explicit copy. `installTooltips()` also migrates legacy HTML `title` hints (including inserted nodes and updated status text) to `data-xrb-tooltip-title`, preventing native tooltip popups. Explicit copy wins over migrated detailed help, which wins over a short button/link `aria-label`. Disabled controls and swatches participate; iframe titles and the document title retain their semantics. Visible tooltips extend `aria-describedby` without replacing existing descriptions and use the top layer over dialogs when supported. Plain text actions without hints remain tooltip-free. Mount once per document and dispose listeners/observers on teardown.
- Shared state/menu classes: `state`, `chip`, `menu`, `toggle`, `row`, `spacer`, `muted`, `mono`.
- Dropdown status marks and details: a generated `.dropdown` may carry `data-marks` (a JSON map from option value to `ok`, `warn` or `err`) and `data-details` (a map from option value to secondary text); each marked option and the closed button then show the shared `xrb-status-dot` before the label, and the detail follows the label as smaller muted `xrb-option-detail` text. The Publisher field marks destinations that are published (green) or deployed but unreachable (amber); Live version marks the verified live release and shows when each release was created.
- Version controls: one shared `#version-menu` (Patch/Minor/Major with the resulting version beside each item) serves every version input; the input's context menu (mouse right-click or the keyboard context-menu key) opens it through `openFloating`, which focuses the first item, and `menuKeyboard` handles arrows and Escape. Package version and publication Next version share this behavior; the menu edits only the draft. The publication row places Live version before Next version. Every workflow surface puts its primary action (Run/Stop, Publish/Update with the confirmed Unpublish, Build) left-aligned in a `project-actions` row below all of its content, while Folder and Open JSON stay at the identity row's right edge. On Publish only, an icon link (the shared `open` icon) precedes JSON and opens the version chosen in Live version: an inspected release's archive, published or not, otherwise the selected destination's live app whenever it is reachable.
- Live version dropdown: the shared dropdown lists every retained release newest first (version or `Legacy (unversioned)`, creation time as detail text), marks the verified live release green and a merely requested one amber, and selects the live one. Choosing another release inspects it: Preview opens its archive and Activate asks "Activate <version> version?" through the shared dialog, explaining in plain words what replaces what; choosing the live (or Not live) entry again ends the inspection. Without history it is a read-only field (`Not live`, `Legacy (unversioned)`, `Not verified yet`).

Legacy control-panel class names remain aliases while markup migrates. New workspace tools should use the `xrb-*` names, mount shared interactive components, and add only product-specific layout CSS. Load IBM Plex Sans/Mono and `design-system.css` before product CSS and application modules to avoid type/layout flashes.

Do not copy tokens or component rules into a tool. Product styles may position a shared component in feature layout, but may not redraw its surface, typography, states, icons, animation, or interaction. Small differences belong in an `xrb-*` modifier variant. If a shared visual changes, change the design system and verify both the control panel and tools.
