# Design: private local projects, public built output

## Boundary and restoration

The private development workspace's `projects/` is authoritative for app source, drafts and archived tests. Recover its tracked tree from the last private pre-migration revision into the linked task worktree, retaining the previous `xrb-panel.json`, project manifests, icons and assets. Compare the three exported apps with the public snapshot for any later approved changes. The maintainer's two edits live in a named stash in the primary checkout. Reproduce those two manifest blobs exactly in this linked task worktree after inspecting their changes, verify their hashes against the stash, and leave the stash and primary checkout unchanged. The restored Launcher remains a native-platform app, so its stored production publisher is dormant unless the maintainer later selects standalone WebXR. Local projects remain selectable for Build, Run, package and Publish. Restore the private workspace's app importers into its existing pnpm lockfile alongside plugin importers, because the same workspace is both project and integration root. Test and archive projects cannot publish; only a deliberately configured WebXR app can. No bulk synchronization of source to the public repository.

The public site repository keeps its complete `main:docs/` output and GitHub Actions Pages settings. The existing public app source is already visible in its history; deleting it from current `main` cannot undo that exposure. Remove current public app source and its build scripts in a reviewed public PR only once local recovery and replacement publication are ready. Never delete the output tree or change the custom domain, inventory, association document, existing routes or HTTPS.

## Publish transaction

Retain the panel's per-local-project manifest identity, slug, automatic build, build-receipt and entry-tree validation. A local Publish builds only the selected project if necessary and passes the verified output to the private production publisher. The publisher checks ownership against the public `docs/` inventory, rejects private files and unsafe paths/links, and updates only that route, marker and publisher-owned metadata in a disposable, plugin-managed checkout of the public site. The user does not maintain a second repository clone. Push a non-force route-scoped `docs/` commit with the maintainer's existing OS-backed credentials, retrying fresh inventory on a competing commit; do not push app source or any other local workspace content.

Once the exact new public commit is confirmed, dispatch a *redeploy-only* public workflow by authenticated API and correlate its run, commit and route. The workflow uses no private-core checkout and deploys the complete committed `docs/` tree as a Pages artifact; a dispatch acknowledgement is not success. Poll the workflow and verify the public HTTPS route, root, inventory and association document before reporting success. Status reads the authoritative inventory and live site, not an earlier local job result. Unpublish requires confirmation and removes only its owned route and explicitly retired associations. Preserve other projects' routes and site files.

The public workflow must stop accepting app-source publish/unpublish operations before local output commits become the sole production site decision writer; it remains the sole Pages deployment writer. Do not make an unguarded second writer or allow an older workflow to overwrite a local publication. Verify current Pages `build_type: workflow`, expected repository and origin before modifying the site. If the public branch is protected against direct writes, stop for a reviewed alternate upload mechanism rather than bypass protection or loosening governance.

## Failure and cutover

A failed build or validation causes no public commit. For a refused push, re-read authoritative state and retry or fail without forcing. For dispatch, deployment or route verification failure after a successful push, revert only the operation's site changes when safe, dispatch the baseline redeploy, verify restoration, and report any inability to restore explicitly. A process crash between push and dispatch must remain distinguishable from deployment success; a recovery/redeploy path reconciles committed and live states without silently overwriting newer decisions. Tests use fake API responses, disposable Git repositories and a simulated origin, never a production dispatch.

Sequence: (1) review the private plan and coordinated public workflow design; (2) restore and locally verify projects, build behavior, identities and stashed-edit disposition in the task worktree; (3) review and merge public workflow changes that retain the existing site and gate old source-driven operations; (4) merge the private implementation only when compatible; (5) have the maintainer update the stable checkout without losing local edits, restart the panel and inspect restored projects; (6) only with explicit maintainer confirmation, run a first real local-panel publication and verify the correlated workflow and live site; (7) remove public source from current `main` in a separate reviewed PR when the new path is proven. At each stage keep the last-known-good `docs/` and do not make an automatic production publication during CI or implementation.
