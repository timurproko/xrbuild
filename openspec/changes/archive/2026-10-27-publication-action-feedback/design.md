# Design

## Immediate platform switching

Apply a selected Platform choice to the in-memory project manifest and re-render the project detail synchronously before sending the manifest update. Project descriptions preload packaging descriptors for every available Platform choice plus standalone publication status, so the optimistic render has the correct fields, validation and publication controls instead of reusing data for the previously selected tab. The resulting native, standalone WebXR or packaged controls therefore appear in the same interaction frame instead of waiting for HTTP and project rediscovery.

Save the same optimistic manifest with the existing mtime guard. Keep one request in flight per project, but do not block later tab clicks: render each choice immediately and replace a queued choice with the latest click. After the active request and authoritative reload finish, persist that latest queued choice; intermediate choices need not reach disk. If the mtime guard reports that a Publisher or other settings save landed first, fetch the latest manifest, reapply only the latest Platform choice and its package identity, and retry with the current mtime so unrelated edits survive and no settings-conflict dialog appears. On validation or network failure, clear the queue and restore or reload authoritative project state rather than leaving an unsaved selection visible.

## Route-change confirmation

Treat `publication.publisher` as the currently selected deployment destination, not exclusive ownership of the app's only deployment. Keep a provider-to-slug map alongside the selected `publisher` and `slug`, migrating existing manifests lazily. Changing Publisher records the old provider's slug, restores the new provider's remembered slug or initially reuses the current slug, and leaves the old provider's route live. Preload status for each installed provider using its remembered identity so switching immediately shows Publish or Unpublish for that provider; switching back restores the provider's slug and exposes its own action. Publisher plugins receive only the selected `{ id, slug }` identity, not the editor's route map. If the full-manifest mtime guard rejects a Publisher or Slug save because a Platform or other background save landed first, fetch the latest project, merge only the desired publication selection and route map into that authoritative manifest, and retry with its current mtime. This preserves unrelated edits and avoids exposing a settings-conflict dialog for publication editing. While any publication edit is pending, retain a tokenized in-memory overlay containing the latest selected publisher, slug and provider status; project refreshes merge that overlay instead of repainting older server values. Disable the publication action for that brief save so a publish/unpublish request cannot target the previously persisted provider. When a publication job starts, pin its selected publisher and slug through completion and status convergence; refreshes update that destination's action and row but never replace the user's selection with another provider. Sequence project-list requests and discard responses superseded by a newer request, preventing delayed status polls from restoring a stale destination after the save completes. If the rebased edit changes a route that the selected provider still reports live or uncertain, keep the route-move confirmation and submit its confirmed retry against the latest manifest rather than the stale one. This permits simultaneous publication through several providers while retaining one active editor selection.

A slug change stays within the selected publisher. Before requesting confirmation for that edit, query the current selected publisher's status. An explicit `unpublished` state is safe to edit directly because no deployed route is being moved. Keep confirmation for published, pending, failed, unavailable or unknown status so a potentially live route is not silently abandoned when status cannot prove it absent.

## Publisher identity in the selector

Use the hostname from each publisher's validated HTTPS `origin` as its visible dropdown label. This identifies the destination directly when several providers or domains are installed and avoids ambiguous environment labels. Continue using the publisher's stable `name` as the option value saved in the manifest; the display-only hostname does not change plugin discovery, routing or publisher selection identity. Fall back to the declared label or stable name only if an unexpected invalid origin reaches the UI.

## Empty package history

Keep the package-history container hidden when no package matches the selected channel and package identity. This removes both its divider and the empty placeholder while retaining package controls and the Build-folder action. As soon as a matching package exists, show the existing list and deletion controls; after the last matching package is deleted, hide the container again.

## Stable publication action

Render one full-size action button in the existing publication action column. Before deployment it is **Publish**; after deployment it becomes **Unpublish** in the same position and with the same action-button geometry. Below the controls, derive a row for every provider whose preloaded status is `published`, not only the selected provider. Use that provider's displayed HTTPS hostname as the row title and its complete deployed or selected URL as the linked detail. Keep all live rows visible while Publisher selection changes; the selector and action control only the selected destination. Published rows do not own separate trash-icon actions. Unpublish still opens the panel's existing confirmation dialog before a job starts.

## Background progress state

Publication remains a background job and does not use the package progress dialog or any new modal overlay. Add explicit `publish` or `unpublish` operation metadata to publication job summaries so the UI does not infer intent from display text. The Build card finds the running publication job for its project and replaces the button label with **Publishing…** or **Unpublishing…**, adds a small inline spinner, and disables that button against duplicate requests.

The existing job event stream triggers a detail re-render when a publication job starts. When a successful publication job changes from running to done, apply a short-lived client override for the selected provider immediately: Publish completion changes the action to Unpublish and expands its deployment block in; Unpublish completion changes the action to Publish and keeps the old block only long enough to collapse it to zero. Re-query project status in the background and retain the override until the provider confirms the expected state or a bounded retry window expires, preventing eventual-consistency delay from making the finished action look stale. Failed jobs continue to rely on authoritative status. Other project and panel controls are not globally disabled while the job runs.

## Styling and accessibility

Use one reusable, current-color spinner inside the action button so it works in both color schemes and keeps the normal compact button width and input-matched height stable. While pending, the centered spinner replaces the visible text rather than resizing the control; an `aria-label` retains Publishing… or Unpublishing… as the accessible operation name. Idle Publish and Unpublish buttons rely on their visible text and omit the tooltip-triggering accessible-label attribute because the actions are self-explanatory. Disable and visibly mute Publisher and Slug for the same interval so the running job cannot diverge from the displayed destination. Once the selected destination is published, keep Publisher enabled to select another provider but make Slug read-only and visibly muted until that selected deployment is unpublished; read-only keeps its value in Publisher-change submissions. Suppress validation messages for locked fields and clear stale publication errors when destinations change. Top-align both labeled fields and offset the action to the input row so an error below one field never pulls the other title or button downward. Publication-row enter and leave animations are decorative, use opacity plus vertical expansion/collapse, and respect reduced-motion preferences. The disabled state communicates that the same publication action cannot be submitted twice. Narrow layouts continue to stack the unchanged publication action column without clipping.
