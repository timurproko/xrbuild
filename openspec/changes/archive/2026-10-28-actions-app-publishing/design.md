# Design

## Existing boundary

The public repository's `main` contains source under `projects/` and generated output under `docs/`. GitHub Pages currently deploys `main:/docs` as a branch-based site. The private publisher checks for `build_type: legacy`, writes `docs/` on public `main`, maintains `.xrb-publications.json` and `.well-known/assetlinks.json`, verifies public route bytes, and reverts a failed publication commit. The public projects' build configs require `XRB_CORE` because the SDK is sourced from the private core checkout. No public Actions workflow or secret exists today.

## Interaction and scope

The maintainer uses **Actions → Publish app → Run workflow** in the public repository, choosing an allowlisted project and operation (`publish` or `unpublish`, with explicit route-removal confirmation). A workflow dispatch is accepted only on the protected public default branch. The workflow reads the selected project's committed manifest for its stable ID and slug; inputs never supply an arbitrary path, ID, slug, remote or shell command. The local control panel remains a local development interface, not a remote project browser; no local clone is required to use the Actions UI. Ordinary project edits still go through reviewed source commits.

## Private core access

The public build needs only the SDK and UI kit sources from the private core, not its `.xrbuild/` workspace. A dedicated GitHub App installation scoped to the private repository with Contents: read issues a short-lived token for checkout; the public repository holds only the App ID and encrypted App key as GitHub Actions configuration. Checkout the private core to a temporary sibling folder at a reviewed ref, set `XRB_CORE` to it, install the public app lockfile frozen and build the selected app. Never run this credentialed job for `pull_request`, an unreviewed ref, or a user-supplied script/path; do not persist checkout credentials. The maintainer must review source and workflow changes before merging because app build scripts on trusted `main` execute inside this job. An exposure test rejects raw private source paths, keys and symlinks from the upload artifact; public app bundles necessarily include compiled SDK runtime code, as the currently published app does. If the maintainer prefers not to grant a public-repository workflow read access to private code, stop before implementation and choose a different authenticated build architecture.

## Site update and Actions deployment

Keep `docs/` as the authoritative complete-site tree and use its existing inventory, root page, CNAME, `.nojekyll`, Digital Asset Links file and untouched routes as baseline. Build only the selected approved app, check `index.html`, file and size limits, unsafe names, and output links. For Publish, validate ID/slug ownership, compute the publisher-compatible content/index hashes, replace only its route and marker, update inventory; for Unpublish, remove only that owned route and its explicit association. Reject any unrelated or unknown route. Artifact upload must contain `docs/` contents at the artifact root, not the source repository or core. Use `actions/upload-pages-artifact` and `actions/deploy-pages` with minimal `pages: write` and `id-token: write` privileges on the deploy job. The build job has read-only repository permissions. Use one concurrency group with no cancellation and a protected production environment; check the Pages target, custom origin and HTTPS before changing any authoritative state.

For durability, stage the publication update as a non-force, route-scoped commit of `docs/` on public `main`; rebase/reapply against fresh inventory if main advanced, never force-push or overwrite source edits. The dispatch workflow deploys the exact resulting `docs/` tree itself (a `GITHUB_TOKEN` push need not trigger another workflow). Wait for Pages and verify root, inventory, association document and marker/index hashes through `https://xrbuild.dev`. If deployment/verification fails, revert only the workflow's site commit when safe, redeploy the last known good tree, verify it, and report explicit failure if restoration cannot be verified. Tests simulate concurrent source commits, collision, stale output, deployment failure and rollback. A separate safe workflow path can redeploy the committed `docs/` baseline without rebuilding an app.

## Cutover and rollback

1. Review and merge the public workflow and private compatibility changes without changing Pages settings. Prepare App credentials and test build, artifact contents, inventory/route equality and deployment behavior in a non-production rehearsal; publishing to production must remain disabled during rehearsal.
2. Pause local production publishing and verify the exact public `main:docs/` tree, inventory and association data. Change Pages **Source** to GitHub Actions only with maintainer authorization. Dispatch a no-change baseline deploy. Verify root, every recorded route, inventory, association document, CNAME and HTTPS before enabling app Publish/Unpublish.
3. After cutover, local publisher status may read the Actions site but local Publish/Unpublish must refuse with a clear message directing the maintainer to the public Actions workflow. No second writer to `main:docs/` is allowed.
4. If the first deployment or domain verification fails, switch Pages back to branch `main:/docs`, verify continuity, and leave local publishing paused until the target is known healthy. Do not delete `docs/`, change DNS or remove the custom domain during this transition.

## Tradeoffs

An Actions deployment removes the need for a local project clone *to publish*, not the private SDK dependency or the requirement to review code executed by the build. Putting build logic directly into the public workflow without limiting secret exposure would give untrusted changes access to private core credentials. Building only a fresh artifact from one app without carrying the existing complete site would drop the launcher, inventory, associations and other routes. A branch-only Pages configuration is simpler and currently works; the workflow is justified by the requested no-clone publishing interface.
