# Two-camera fusion — operator test handoff

**Stage 6 software is implemented. Physical fusion acceptance is YOUR next test; Stages 7–9 are paused until you test and explicitly confirm proceeding.** Automatic calibration now connects directly to combined output: **Calibrate → Start calibration → Done starts Fused with both hand models**. It measures B→A geometry from the marker and uses clearly labelled SDK System Time diagnostic matching, not an identity transform or fabricated zero-offset calibration. Physical alignment, accuracy and exposure synchronization still need real evaluation. Application publishing, anatomical fitting, new temporal filters and alternative models are not included.

## Open and start

Use the running **http://127.0.0.1:5190/**. If it is not running:

Use the normal panel's `/hand-tracking/` tool after explicit bundled setup. Fusion is an optional workflow requiring
separately configured model/device dependencies and explicit camera Start; source approval does not activate it.

1. Fix both cameras with overlapping views. In **Capture → Two cameras · fusion**, choose two different full serials and the desired actual RGB8/Z16 resolution/FPS. The browser remembers ordered camera/profile choices, never capture permission. Two authenticated viewer-managed slots require no second terminal or pasted keys.
2. Press **Calibrate cameras… → Start calibration**. Show one flat tag36h11 marker to both cameras, handheld or tabletop. No ID, size, uncertainty or placement fields. Normal marker movement is allowed; relative camera pose, matched-frame motion risk and later-frame residuals are checked automatically. See [marker preparation and integrity](marker-calibration.md).
3. Press **Done**. It applies the measured rigid B→A transform, enables both hand-model workers, selects **Fused** and starts the current runs. After the two-second warm-up, agreeing joints combine; A tracking loss uses current registered B joints, reverse loss uses A, and both lost means no point. The matched-frame status shows actual **both / A-only / B-only** counts. Close cancels the pending result instead.
4. Stop/Start retains this automatic rig only for the same serial/profile identities, obtaining fresh current-run clock bindings. Source/profile changes invalidate approval; moving a camera requires recalibration. Capture/import/reload never starts automatically. Imported/manual surveys still need explicit rig confirmation; the [manual ≥6-fit/≥3-check survey](camera-calibration.md) retains its reference-uncertainty and measured-timing gates.
5. Camera A/B remain source-inspection modes. Registered B, Best View and Fused use **A optical metres** only after the actual spatial/profile/rig checks. A spatial JSON stays spatial-only (`fusionEnabled:false`); the live controller supplies the separate diagnostic clock policy. No camera-to-panel/application coordinates are inferred.

CPU/GPU settings apply at camera Start. A paired replay uses the original stored model observations, not a silently re-run model. GPU means the existing MediaPipe WebGL delegate, not guaranteed hardware acceleration or a speed win. Depth sampling in this two-view mode uses the fixed Stage 4 defaults (5×5 patches, 72% coverage and existing rejection bounds); each frame records the actual settings.

## Diagnostic reported-clock matching versus measured timing

The simple automatic workflow pairs the two local native streams in the SDK's **System Time** namespace (the pinned SDK defines it relative to the OS system clock). This is explicitly a **reported-clock-only diagnostic preview**, not an exposure-alignment certificate: exact run/profile/serial binding, bounded reported color-time difference plus both intra-camera skews, ≤150 ms receipt separation/output age, order/regression and gross clock-discontinuity checks remain enforced. The preview creates no events or offset; temporal uncertainty and effective exposure-time budget are null. The viewport says **timing unverified**. Unsupported clocks fail closed. Do not equate known timestamp namespace with simultaneous exposures.

### Advanced common-event measurement and same-input benchmark

The current devices expose depth-module **Inter Cam Sync Mode**, range 0–260, current/default 0; the RGB sensors do **not** expose that option. Global Time Enabled reads 1 on both sensor types. These were **read-only SDK queries**, not a hardware trigger/wiring test. The Hand Tracking Input diagnostic changes no hardware sync options and does not claim simultaneous RGB/depth/inter-camera exposure. A depth-sync capability or equal SDK `System Time` labels does not synchronize RGB. A justified timing qualification requires an explicit **common visual-event measurement**; the simple live preview does not pretend to supply one.

Use at least three distinguishable physical events visible in both cameras (for example a controlled, identifiable flashing target), spanning ≥200 ms. Establish an honest per-view event uncertainty, including frame sampling/skips, exposure/readout ambiguity and your event-selection method. **Do not derive that bound from advertised 30 Hz alone** or type a smaller number merely to pass. If a positive bound ≤25 ms cannot be justified, improve the timing experiment/acquisition first; individual camera inspection and raw paired recording remain available.

- **Live selection:** in Settings → Common-event timing, Freeze A and Freeze B at RGB frames depicting the **same event**, check the match confirmation and Add common event. Resume views before choosing another event. Frozen 2D views hide the combined pose; they do not freeze or secretly record the camera acquisition.
- **Recommended saved-input selection:** record a short paired clip containing the shared events, stop recording, then **Replay paired clip**. Both cameras/models stop. Enable **Select independent saved source frames**, inspect each source's zero-based frame index and choose the matching event in A and B. The RGB labels identify their original color frame/timestamp. Add each confirmed match. Independent timing inspection hides the combined pose and benchmark timeline; no asynchronous pictures are presented as a fused pair.
- Describe the event/reference and enter its independently assessed per-view uncertainty. **Fit timing** recomputes B→A reported-color-clock offset as the median matched event difference. The conservative bound is twice the per-view uncertainty plus the maximum event-offset residual (hard maximum 60 ms). Duplicate, unordered, too-short, excessive or unsupported-domain evidence is rejected.
- Only SDK System/Global Time with compatible domains is supported; unmapped hardware clocks are refused. Timing is bound to **both exact native run IDs**, serial/profile hashes and the event interval with **at most 60 s extrapolation on either end**. Restarting cameras requires new event measurements. Old setup can still be used with its original paired recording. An expired/regressed clock clears fusion rather than filling from old poses. This remains appearance/report-clock alignment, **not verified exposure synchronization or a drift/latency certificate**.
- Turn off independent frame inspection / Resume views after selection. For a saved clip press **Rebuild Best View vs Fused** after changing setup/timing/options. Changes invalidate the old comparison; it cannot be displayed as a result of the new settings. Export intervals/reports before changing setup if you need to keep them.

Export **fusion setup** separately from media. The bounded 128 KiB scalar JSON contains recomputed spatial/timing evidence and exact bounded fusion settings, not images, hand poses or credentials. Signed zero and checksums are preserved. Import never starts a camera/model or supplies physical confirmation. Every paired media import also resets the rig confirmation; confirm the survey applies to that recording before rebuilding.

## Compare modes on identical inputs

Done selects **Fused** so calibration produces actual combined reconstruction immediately. The initial uncalibrated view is still Camera A. Compare **Best View** deliberately and keep it if fusion worsens transitions, loss/reacquisition, jitter or lag; automatic selection is not a quality/accuracy claim. The same-input benchmark requires measured common-event timing, not merely the diagnostic clock preview.

- Timestamp matching keeps at most eight **scalar processed observations**, not RGB/depth buffers, per source. It counts duplicate RGBs, invalid/skipped inputs and bounded queue omissions. Event-qualified matching uses the reported B→A color-time mapping, event uncertainty **and both reported within-camera RGB/depth skews**, default total budget 75 ms (hard maximum 100 ms). The automatic live preview uses the same bounded queues with the shared SDK System Time reports and both intra-camera skews, but reports only a **reported-clock budget**, never an unknown exposure uncertainty as zero. Source receipt separation and live output age are bounded at 150 ms by default. Bad within-camera pairs are still rejected by Stage 4's 50 ms guard; startup guards are not loosened.
- Associate up to two source hands each using a one-to-one registered palm geometry assignment, a weak handedness clue and bounded identity/motion continuity. Never equate source-local IDs. Ambiguous crossings are not forced into merges or duplicated across nearby views; conservative source-A observations remain explicitly marked ambiguous. IDs remain diagnostic/best-effort, not physical identity guarantees.
- Best View selects one source per associated hand using current depth support/quality and selection hysteresis. Fused uses only current valid supporting joints: both agreeing sources get normalized depth-quality weights; one valid source contributes alone; neither valid means no point. A/B registered joint distance above 40 mm is rejected, not averaged. Motion bounds reject implausible changes; no interpolation, old-joint filling, anatomical constraints, filtering or prediction are introduced.
- Points → landmark inspector shows native/registered XYZ or current per-joint A/B weights/rejection. Joint colors: A cyan, B purple, both gold. These weights are **not confidence/probability**. Optional source overlays use the same qualified matched pair in common A coordinates. Stats show actual backend, source skips, named matched color frames, timing budget, ambiguity/rejections and registered cross-view joint-distance summaries in metres. Disparity combines motion, model, surface and calibration effects; it is not independently measured joint accuracy.
- Live RGB previews are each source's latest processed image; they may be newer than the named matched output pair. Saved matched-pair playback decodes and commits the **exact two source frames** together, with their own overlays. All geometry is registered visible surface at a model landmark, not an anatomical joint center.

### Paired media and benchmark

1. Press **Record → Record both** explicitly. Shared limits are **20 seconds, 600 total A+B frames and 128 MiB including container overhead** — not twice those budgets. There is at most one compressor per source, two total, with pre-Record sequence/page fences and independent source/encoder/invalid/limit omission counters. Original RGB8, original/aligned Z16, model observations, SDK profiles/calibration, native clock domains/frame counters, page origin and original sampling are retained for each source. This is a bounded processed-input sample, not a full sensor-frame archive.
2. Stop recording; export **`.handpair`** to keep it. One clip total is allowed across single-camera and paired modes. Delete the previous single-camera clip before paired recording/import, and vice versa. Nothing is saved/uploaded automatically. A missing stream does not yield a fake complete pair.
3. Replay stops both cameras/models. Original input is immutable; both reconstruction histories are rebuilt sequentially and Best/Fused association/motion histories start independently on the **same accepted source pairs**. Play/pause/seek/step/speed work without model/camera startup. Unmatched intervals/omissions are reported, not invented as synchronized samples.
4. **Benchmark A = Best View, B = Fused** (not physical camera A/B). Annotate visibility, expected hand count and stationary intervals over the matched-pair slots. Use the [benchmark definitions](benchmark.md). Availability distinguishes lost from unavailable/unknown gaps; jitter includes residual motion; accuracy, exposure and capture-to-photon remain unknown. Intervals bind to original media **and the exact paired timeline**, so a different matching cannot silently reuse frame-index labels.
5. Export benchmark/intervals and fusion setup separately. The benchmark includes content/configuration/model/hardware identities, recorded per-source sampling, source/association/rejection counters, named pair indices, registered disparity and qualified timing components. Fusion/selection compute duration is measured separately on the current monotonic clock; it excludes queue waiting, sensor/transfer/model/render time and is not live capture latency. Reports contain **no raw hand coordinates or images**; the paired media itself is sensitive RGB/depth/pose data. Verify exports on disk. Delete releases memory, models/decoders and URLs, not files already exported. Keep exports private/outside source/public/cloud-sync directories and remove them manually when evaluation ends.

### Container contract

`XRBPAIR1` + little-endian uint32 JSON length + schema-owned pair manifest + uint32 A-file length + complete original `.handtracking` v2 A file + uint32 B-file length + complete original v2 B file. The manifest declares version 1, shared-page **receive-only** timebase, unique ID, total frame count/duration, page time origin, private evaluation and `exposureSyncVerified:false`. It never equates common browser receipt clocks with exposure alignment. Nested manifests are admitted before packet decode; combined caps, distinct serials/shared page provenance, overlap, clocks, lengths, hashes, source identity, decompression limits and trailing bytes are validated. No guessed transform/timing is embedded in media; scalar setup is a separate explicit export.

## Your acceptance test — stop here afterward

Use the same fixed rig and paired recording for Camera A/B, Best View and Fused. Test stationary open hand; slow/fast reaches; view edges; palm rotation/curls; one-view occlusion and both-view loss; two-hand crossings. Inspect source alignment, motion disparity, invalid tips and source-switch jumps. Compare annotated availability/loss/censored reacquisition, stationary variability, segment plausibility and actual software timing on the same input. A ruler/independent reference is required for accuracy; a lower jitter number alone is not an accuracy win. Also check USB reconnect, sustained station load, IR interference and real finger-depth quality. **Do not proceed to Stage 7 until you confirm this test.**

## Verification and limits

232 focused tests pass, including numerical/degenerate calibration, timing/run/expiry/integrity, assignment ambiguity, outlier/motion/missing-joint behavior, queue/history bounds, shared frame/byte/time caps, cancellation, paired lossless round trips and independent same-input reconstruction. Development/production browser fixtures use two **generated** devices/timestamps/depth plus the official public hand image with two real model workers: setup/temporal UI, contributions, one-view/both-view holes, exact replay, config invalidation, scalar benchmark, corruption, import without capture, rig reset, foreign-owner isolation and failed-second-camera rollback pass with zero exceptions. This is software evidence, not physical fusion acceptance.

The [current marker integration](marker-calibration.md) adds native ID/rotation/canonical-corner and small/low-contrast CTests, handheld relative-pose checks and generated development/production **Calibrate→Done→Fused** fixtures at 424×240, 640×480 and 1280×720. With two real model workers these verify actual both-source contributions, A tracking loss/B-only (42 supported points), reverse loss/A-only (42), both loss clearing 3D, recovery, fresh-run restart and cleanup, with zero exceptions. The reported-clock preview keeps unknown timing/physical accuracy explicit; none of these fixtures measures the operator's actual target/rig.
