# Local projects, public site

The independent private `.xrbuild` repository owns the development workspace, including local apps, drafts, tests, archived diagnostics and private integration plugins. Authorized developers clone it at the core checkout's ignored `.xrbuild/` path; its files and Git history do not belong to core. See [Workspace split](workspace-split.md) for migration and recovery. The separate public [`xrbuild.dev`](https://github.com/timurproko/xrbuild.dev) repository holds the published site output in `main:docs/`. GitHub Pages deploys that complete tree through GitHub Actions at `https://xrbuild.dev` with the existing custom domain and HTTPS.

Start the core's explicit repository-workspace panel with `start-repo.vbs` or the repository-mode shortcut. Projects and archived tests appear in the ordinary Projects/Archive tabs. A configured local standalone WebXR app has a Publish surface with Publisher, Slug and Publish; once a route is deployed the primary action still reads **Publish** (an update in place, confirmed with the version, destination and what it replaces) and **Unpublish** stays a separate, confirmed action. Clicking Publish builds only the selected app when needed, validates its output and stable identity, and sends **only its built route and publisher-owned site metadata** to `xrbuild.dev:main:docs/`. With the production publisher each Publish or Update is a release with a **Next version** (Patch/Minor/Major from the shared menu; `0.1.0` without history, otherwise the patch after the highest retained version), independent of the package version. **Live version** is a dropdown of every retained release, newest first, with the verified live one marked and selected. Choosing another release only inspects it: the open icon in the identity row opens that release's public archive in a new tab, **Activate** redeploys its exact output at the same URL after confirmation, without rebuilding, and **Delete** removes that release and its archive after confirmation (the live version cannot be deleted). Choosing the live release again returns to Update and Unpublish. An existing unversioned deployment is shown as **Legacy (unversioned)** and is retained as a selectable release on its first Update. Unpublish removes the live route but keeps the release history and its public archives. The Publisher dropdown marks each destination that is live with a green dot, and the workflow header shows the live URL; with several live destinations it shows "N published" and opens a menu with one link per destination. Draft and test projects are never uploaded by default. No separately maintained local `xrbuild.dev` checkout or public Actions UI interaction is necessary.

The private publisher uses a disposable cache and the maintainer's existing OS-backed Git/`gh` login. It rejects unsafe files, collisions, wrong hosting, a public-source writer still being enabled, or an unavailable workflow. A non-force, route-scoped public output commit is followed by a correlated redeploy-only Actions run. The panel shows success only after the run completes and the full live site and selected route verify. Status and errors come from authoritative remote state, not dispatch acknowledgement. The workflow receives neither app source nor private-core credentials; the browser receives no token.

## Coordinated transition and recovery

The previous migration put app source in the public repository. It remains visible in public Git history even after deletion from current `main`. Its current source tree must be removed only in a **separate reviewed public PR** after local restoration and a maintainer-authorized first publication prove the replacement flow. Never rewrite public history or delete `docs/` as part of this change. Restore and reconcile the maintainer's preserved local manifest edits separately; do not pop the old stash onto the updated primary checkout.

Keep Pages on GitHub Actions, keep `main:docs/`, `CNAME`, origin-root files, route inventory and associations, and retain the live site before and throughout transition. The public workflow must become redeploy-only before local output publication is enabled; the plugin refuses to write while the old public-source Publish/Unpublish writer is present. Public Pages settings, credentials and production operations require separate maintainer authorization. If a deployment or verification fails, inspect the correlated run, inventory and site before retrying; the publisher attempts a safe revert and baseline redeploy and does not falsely report restoration when it cannot verify it.
