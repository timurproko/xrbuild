# Desktop setup checklist

Choose **Rebuild** from the panel menu. Before a build starts, XR Build checks CMake, a supported C++ compiler, the desktop SDK, pinned core native libraries and the host runtime. Missing prerequisites open **Desktop setup** instead of creating a predictably failing build job. Browser-only use does not require this setup. Optional plugins can have their own additional prerequisites; the generic checklist does not install device/model or private plugin dependencies.

## Explicit actions

Steps have fixed positions: core native libraries first, then one **Build tools** section containing the CMake/C++/SDK checks. There is no redundant Host runtime Missing row: **Rebuild** creates that output. Both sections use matching compact bordered cards, equal padding and right-aligned Install actions in their headers. Core native libraries is a compact title/status/action summary without descriptions or an included-library list. Header Install/Repair buttons match the Missing tag's full width, height and typography without changing its size, with vertically centered controls and consistent heading/helper/content spacing. They retain button styling, with comfortable separation before the footer. The main setup header uses a decorative setup icon and the same readable muted description style as progress dialogs; action captions such as “Install desktop build tools…” start with a capital letter. Routine descriptions and output links are omitted from both cards. Status badges align right; included toolchain checks use smaller, lighter text without repeated instructions. There is no blanket setup-in-progress banner: an unknown status or lock does not confirm an installer is running. Connection errors say “Connection lost. Refresh to reconnect.” Installing or refreshing changes a row's status, never its position—even after reopening or reloading. Toolchain and core native libraries can be installed in either order; rebuild comes after both are ready.

- **Refresh** reads installed state without downloads or workspace initialization. While checking, the button is disabled and shows **Checking...**; install/rebuild actions and duplicate refreshes are blocked until success or error restores the normal controls. Tools installed outside the launcher's old PATH are checked in supported installation locations.
- **Install** (or **Repair** for partially installed tools) in the Build tools header installs the C++ workload, CMake and SDK together. It uses the system package manager's standard trusted source and one fixed desktop build-tools package when available. Otherwise it downloads the fixed official bootstrapper into fresh user-owned installer storage, checks its valid provider signature and download hash while preventing file modification/replacement, and launches it through the normal Windows administrator prompt. Only approved HTTPS redirect hosts, bounded downloads and fixed component/no-reboot/wait arguments are allowed. The package installer may be rerun to repair missing components, but package hash checks are not disabled. No browser-supplied command, executable path, package ID, URL or installer arguments are accepted.
- **Install** for core native libraries downloads the existing pinned inputs into a fresh selected-user-workspace `build/native-deps/` generation. The standard fetcher verifies its archive/file hashes. A checked source-bound receipt activates completed output; installed product `third_party/`, source files and lock pins are not changed. Failed and previous generations are preserved, not cleaned up.
- **Rebuild** becomes available when its core prerequisites pass. It remains a separate explicit action and uses the existing immutable host runtime/cache publication flow. It does not create a project or start an application automatically.

Clicking **Install** or **Repair** explicitly requests that installation; there is no separate checkbox or disclosure paragraph in the checklist. Opening or refreshing the checklist never installs anything. Large downloads and a trusted Windows administrator prompt may be necessary. The panel uses the shared progress modal and Jobs log rather than opening a terminal. A background installer is not a way around elevation or license requirements.

There is one setup flow: **Install/Repair → background progress → verified Ready**, without a manual-install state or website link. Failed jobs retain output and the same explicit retry action. If automatic setup is unavailable or prerequisite state is unsafe, the checklist shows **Blocked** and its concrete reason below the cards; resolving refresh checks clear that message. Installed native tools are reused where supported; the panel does not change global PATH.

## Failure, restart and concurrency

Installation output remains in the shared progress modal and **Jobs**, with distinct toolchain/native-library job identities. The prerequisite checklist contains no View setup output links.

Setup failures remain actionable through progress and Jobs. Interrupted status reads are retried up to three times, but installation requests are never automatically repeated. A lost status connection does not mean installation failed: recovered job results clear obsolete connection errors; if reconnection fails, the checklist explains that status is unconfirmed and offers Refresh/Jobs rather than prompting blind reinstallation. A successful exit alone is not enough: the actual tool/dependency checks must pass. If an installer reports a restart requirement, its badges and progress result remain visible without a duplicate red restart notice in the checklist. Restart Windows yourself when convenient and refresh the checklist afterward. No automatic reboot is requested.

Closing a browser tab does not cancel setup. After reloading, choose Rebuild again to inspect the existing setup job instead of starting a duplicate. The panel refuses conflicting jobs/native launches and refuses quit/restart while its system setup is running, even with a force-confirm flag. A per-user setup lock prevents competing panel installers; another active lock is not removed automatically. Close other native build tools before changing the system toolchain. External installer/OS coordination remains authoritative.

Changed, malformed, linked or foreign dependency/restart records are preserved and reported for review. Do not remove a setup lock just to make the UI proceed; first verify its previous writer stopped. There is no automatic cleanup or rollback of unrelated software, user settings, signing identities, private data or old dependency generations.

## Design review

The **Design** app-menu entry is shown for Dev/repository-development launches, not normal user/auto launches, directly after Settings and before the Restart/Rebuild separator. Its gallery at `/design` uses the standard XR Build product header and a case dropdown (Main for shared components, Install dependencies for this checklist) without a visible Cases label or subtitle, with compact plain checklist/progress rows. It uses the real shared dialogs against in-memory mocks, with no real case API requests, installs or builds. The gallery shell offers the same registered-tool links and explicit Restart/Rebuild actions as the app; tool menus discover those same links and return to the actual serving panel, not a build-time address. Its background is plain behind the dimmed dialog. Use the browser window to resize/reload; appearance comes from **Settings → Apps (core) → Theme** when the gallery is opened on the same panel origin. A separate-origin preview retains its own browser-local preference.

## Validation boundary

Automated checks use synthetic executables, fake installers/downloads, disposable user state and real-browser UI fixtures. Direct-installer tests exercise system signature/hash checks and synthetic elevation only; unsigned, changed, wrong-provider, redirected and oversized downloads cannot reach execution. They do not install software, elevate, reboot, build hardware integrations or grant distribution/license approval. Real administrative installation, native compiler completion and device-specific acceptance must be verified separately on an explicitly provisioned machine.
